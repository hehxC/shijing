# 石境 AI 应用落地计划

## 1. 计划目的

本计划用于将“石境：AI 造园顾问”从功能较完整的技术项目，推进为可部署、可观测、可评测、可供真实用户试用，并能通过业务数据证明价值的 AI 应用。

落地不以继续增加 Agent、模型或框架为主要目标，而以以下结果为判断标准：

- 真实用户可以独立完成一项有价值的业务任务；
- 系统在生产环境中能够稳定运行，并能处理失败、超时和滥用；
- AI 输出质量、调用成本和业务效果能够量化；
- 用户反馈可以持续进入评测集和产品迭代；
- 项目最终能够形成可演示、可复盘、可写入简历的真实案例。

## 2. 产品定位

### 2.1 目标产品

面向石材门店销售和小型庭院设计师的 AI 售前方案助手。

### 2.2 核心业务问题

传统庭院初步方案通常需要反复沟通现场条件、材料偏好、风格和预算，并由设计人员花费较长时间制作效果图。石境希望将这一过程压缩为：

> 上传现场照片和候选石材 → 快速生成初步效果图 → 查询真实材料与价格 → 输出可用于销售沟通的方案。

### 2.3 目标用户

- 石材门店销售人员；
- 小型庭院设计师；
- 有庭院改造需求、希望快速预览效果的业主。

第一阶段优先服务石材门店销售和庭院设计师，因为其使用场景更明确、材料数据更真实、业务价值更容易衡量。

### 2.4 核心价值

- 缩短初步方案制作时间；
- 降低售前沟通成本；
- 直观展示石材铺装和庭院风格；
- 使用真实材料数据回答规格、单价和预算问题；
- 保存方案及修改过程，支持后续持续沟通。

## 3. MVP 范围

### 3.1 唯一核心流程

```text
注册/登录
  → 创建庭院方案
  → 上传庭院空间图
  → 选择庭院风格
  → 上传或选择石材
  → 生成效果图
  → 通过文字继续修改
  → 查看材料清单和预算参考
  → 保存并恢复历史方案
```

### 3.2 第一阶段非目标

- 不增加更多 Agent；
- 不接入更多模型供应商；
- 不生成专业施工图；
- 不承诺结构安全或规范审批结论；
- 不建设社区、作品分享和复杂运营后台；
- 不加入支付系统；
- 不为了展示技术而继续扩大 RAG、MCP 或多 Agent 范围。

## 4. 当前基础与主要缺口

### 4.1 已具备的基础

- 完整的用户注册、登录和访问控制；
- 庭院空间图、石材参考图和效果图管理；
- 多轮会话持久化和跨设备恢复；
- 意图路由、文本问答、视觉分析和效果图生成；
- 基于数据库的材料查询与估价；
- 带来源引用的领域知识检索；
- MySQL、SQLAlchemy 和 Alembic 数据库迁移；
- 图片存储抽象和受保护的图片读取接口；
- 路由、SQL、RAG 检索和 RAG 回答评测；
- CI 回归门禁；
- 当前 23 个单元测试全部通过。

### 4.2 主要落地缺口

| 维度 | 当前状态 | 落地缺口 |
| --- | --- | --- |
| 核心业务流 | 功能较完整 | 需要冻结范围并建立端到端验收 |
| AI 质量 | 已有路由、SQL、RAG 评测 | 缺效果图和完整任务评测 |
| 数据 | 有内置知识和材料库 | 缺真实商家材料、价格和案例 |
| 部署 | 以本地运行方式为主 | 缺容器、正式环境和对象存储 |
| 可靠性 | 有部分异常处理 | 缺限流、统一重试、降级和健康检查 |
| 可观测性 | 有路由决策日志 | 缺统一请求链路、Token、成本和错误统计 |
| 用户闭环 | 能生成、修改和保存 | 缺满意度、采纳率和人工修正反馈 |
| 业务证明 | 暂无真实试点指标 | 缺真实用户案例和量化结果 |

## 5. 总体实施计划

总体计划按四个阶段推进，每个阶段约一周。实际进度以阶段验收结果为准，不以自然周结束作为完成标准。

## 5.1 第一阶段：受控试用版本

### 目标

将现有系统整理为可以安全邀请首批真实用户试用的版本。

### 主要工作

- 冻结 MVP 核心流程和非目标；
- 建立请求 ID 和结构化日志；
- 记录 AI 调用耗时、Token、成本和结果；
- 增加用户级限流、每日额度和并发控制；
- 统一图片格式、体积、像素和数量限制；
- 为模型调用建立超时、有限重试和降级策略；
- 建立 10 条端到端核心流程验收案例。

### 阶段完成标准

- 新用户可以在 5 分钟内完成第一份方案；
- 10 条核心流程至少 9 条成功；
- 100% 图像生成调用可追踪耗时、状态和成本；
- 超额请求在调用模型前被拒绝；
- 生成失败后可以安全重试；
- 不存在的材料价格保持 0% 编造率；
- 日志中不出现 API Key、Token、密码和完整图片 Data URL。

## 5.2 第二阶段：生产部署能力

### 目标

建立可重复部署、可恢复、支持正式环境运行的基础设施。

### 主要工作

- 增加 `Dockerfile` 和生产启动配置；
- 提供 `.env.example` 和环境变量说明；
- 增加 `/health/live` 与 `/health/ready`；
- 将数据库迁移从应用启动过程调整为独立发布步骤；
- 增加 OSS、S3 或 MinIO 图片存储适配器；
- 配置 HTTPS、域名、数据库备份和恢复方案；
- 建立开发、测试和生产环境隔离；
- 验证容器重建、多实例和图片持久化行为。

### 阶段完成标准

- 新环境可按文档一次部署成功；
- 应用实例重建后历史图片和会话不丢失；
- 健康检查能够区分进程存活和依赖可用；
- 数据库迁移可审计、可重复执行；
- 数据库可以从备份恢复；
- 配置和密钥不进入代码仓库。

## 5.3 第三阶段：业务评测体系

### 目标

把当前模型及模块评测扩展为完整业务任务评测，证明用户能否获得可用方案。

### 主要工作

- 建立 20～30 条端到端业务评测案例；
- 覆盖生成、追改、分析、材料查询、估价和失败恢复；
- 建立效果图人工评分表；
- 邀请庭院设计师或石材销售参与评分；
- 记录现场结构保真度、材料还原度和风格一致性；
- 评估方案可施工性和销售沟通价值；
- 将线上失败案例和用户修正清洗后加入评测集；
- 将关键端到端指标加入发布门禁。

### 端到端重点场景

- 指定石材是否被正确使用；
- 修改要求是否只影响目标区域；
- 材料清单是否与用户选择一致；
- 预算是否基于数据库真实价格；
- 缺少价格数据时是否明确拒绝编造；
- 模型失败后是否能够恢复和重试；
- 恢复历史会话后是否能够继续修改。

### 阶段完成标准

- 端到端成功率达到预设门槛；
- 图片质量有人工基线，而非只依赖 LLM Judge；
- 每次版本变化可以对比任务成功率和质量变化；
- 已知失败场景均有测试或评测覆盖。

## 5.4 第四阶段：真实用户试点

### 目标

通过真实案例验证用户价值，并形成可量化的落地结果。

### 试点对象

- 1 家石材门店；
- 1 位庭院设计师；
- 1～3 位真实庭院改造用户。

### 主要工作

- 准备真实材料、价格和庭院案例；
- 邀请用户完成 15 个以上真实任务；
- 记录原流程耗时和 AI 流程耗时；
- 记录生成次数、失败次数和模型成本；
- 记录方案是否被采纳；
- 收集人工修改内容和最严重错误；
- 根据高频问题完成一轮产品修正；
- 整理演示视频、架构说明和落地复盘。

### 关键业务指标

- 首份方案完成时间；
- 完整任务成功率；
- 单份方案平均模型成本；
- 平均效果图生成次数；
- 用户主动重试率；
- 方案采纳率；
- 用户满意度；
- 相比旧流程节省的时间；
- 用户再次使用意愿。

### 阶段完成标准

- 完成至少 15 个真实案例；
- 能够量化时间、成本、成功率和采纳率；
- 能够列出前三类真实失败及其改进结果；
- 形成一份可公开展示的脱敏落地报告。

## 6. 第一周具体执行计划

第一周目标是完成“受控试用版本”。以下任务建议作为一个父 Issue 下的 8 个子 Issue 管理。

## 6.1 任务一：冻结 MVP 核心流程

**优先级：** P0  
**预计时间：** 0.5 天  
**依赖：** 无

### 工作内容

- 确认目标用户、核心问题和唯一主流程；
- 明确第一阶段的功能范围和非目标；
- 为核心流程的每一步定义正常结果和失败结果；
- 确认页面入口、操作顺序和用户提示保持一致；
- 删除或隐藏会干扰主流程的实验入口。

### 产出

- MVP 范围说明；
- 核心流程图；
- 非目标清单；
- 第一版成功指标。

### 验收标准

- 陌生用户仅根据页面提示可以完成一次完整流程；
- 一个新需求是否属于 MVP 可以被明确判断；
- 主流程不存在相互竞争或含义重复的入口。

`operation` 使用稳定枚举：

### 用户任务记录

建议增加 `design_runs`：


### 数据安全约束

- 模型价格集中配置，不散落在业务代码中。

### 验收标准

给定一个 `request_id`，可以查清一次用户操作经过了哪些 AI 调用、花费多久、是否失败以及大致成本。

## 6.3 任务三：建立统一 AI 调用观测模块

**优先级：** P0  
**预计时间：** 1 天  
**依赖：** 任务二

### 工作内容

建立统一观测接口，内部负责：

- 生成或接收 `request_id`；
- 记录开始和结束时间；
- 记录成功或失败状态；
- 提取 Token usage；
- 记录重试次数；
- 对异常进行分类；
- 根据集中配置估算成本；
- 将记录持久化。

优先接入：

1. 效果图生成；
2. 视觉分析；
3. 文本与 SQL Agent；
4. 意图路由；
5. RAG embedding。

建议异常分类：

```text
timeout
rate_limited
authentication_failed
provider_unavailable
invalid_request
content_rejected
database_error
storage_error
internal_error
client_cancelled
```

### 验收标准

- 成功调用产生完整观测记录；
- 模型异常也产生失败记录；
- 流式响应被用户中断时能够标记；
- 观测写入失败不会导致主业务再次失败；
- 单元测试不调用真实模型。

## 6.4 任务四：增加请求 ID 和结构化日志

**优先级：** P0  
**预计时间：** 0.5 天  
**依赖：** 任务二

### 工作内容

- 增加 FastAPI 请求中间件；
- 接受客户端 `X-Request-ID`，不存在时由服务端生成；
- 将请求 ID 放入当前请求上下文；
- 在响应头返回 `X-Request-ID`；
- 所有关键业务日志包含该请求 ID；
- 日志使用稳定事件名和结构化字段。

示例：

```json
{
  "event": "image_generation_failed",
  "request_id": "example-request-id",
  "user_id": 12,
  "session_id": "example-session-id",
  "operation": "image_generation",
  "latency_ms": 18234,
  "error_type": "provider_unavailable"
}
```

### 验收标准

- 浏览器返回的请求 ID 可以关联数据库观测记录和服务日志；
- 日志中不存在 API Key、Authorization Token、密码和图片原始数据。

## 6.5 任务五：增加用户级限流和生成额度

**优先级：** P0  
**预计时间：** 1 天  
**依赖：** 任务一

### 初始限制建议

| 操作 | 初始限制 |
| --- | ---: |
| 登录 | 每 IP 每分钟 10 次 |
| 注册 | 每 IP 每小时 5 次 |
| 普通聊天 | 每用户每分钟 10 次 |
| 视觉分析 | 每用户每分钟 3 次 |
| 效果图生成并发 | 每用户最多 1 个 |
| 效果图生成额度 | 每用户每天 10 次 |
| 图片上传 | 每用户每分钟 10 次 |

以上限制应通过配置调整，不在路由中硬编码。

### 实现要求

- 限流结果包含 `allowed`、`remaining`、`retry_after` 和 `reason`；
- 超限返回 HTTP `429` 和 `Retry-After`；
- 前端明确展示额度不足或稍后重试；
- 效果图生成支持 `Idempotency-Key`；
- 用户双击、浏览器重试和同会话并发不会产生重复生成；
- 单实例试用可使用进程内实现，正式环境预留 Redis 适配点。

### 验收标准

- 第 11 次超额生成不会调用模型；
- 并发点击不会生成多份结果；
- 不同用户额度相互隔离；
- 429 不会被前端显示为普通服务器错误。

## 6.6 任务六：统一图片输入限制

**优先级：** P0  
**预计时间：** 0.5 天  
**依赖：** 无

### 建议规则

- 单张图片最大 10 MB；
- 允许 JPEG、PNG 和 WebP；
- 解码后验证真实图片格式，不只相信客户端 MIME；
- 最大像素数限制为 25MP；
- 庭院空间图最多 1 张；
- 石材参考图最多 20 张；
- 文件名不参与服务器对象 key 的生成；
- 明确决定过大图片是自动压缩还是直接拒绝。

### 必测场景

- 文本文件伪装为图片；
- 无效 Base64；
- 超大图片；
- 解压炸弹；
- 空图片；
- 路径穿越；
- 重复上传；
- 超过 20 张材料图。

### 验收标准

非法图片在进入数据库、图片存储和模型调用前被拒绝，并返回明确错误信息。

## 6.7 任务七：建立超时、重试和降级策略

**优先级：** P0  
**预计时间：** 1 天  
**依赖：** 任务三

### 初始策略建议

| 操作 | 超时 | 重试 |
| --- | ---: | ---: |
| 意图路由 | 10 秒 | 1 次 |
| 文本模型 | 60 秒 | 1 次 |
| 视觉分析 | 90 秒 | 1 次 |
| SQL 查询 | 15 秒 | 0～1 次 |
| RAG 检索 | 5 秒 | 0 次 |
| 图像生成 | 240 秒 | 最多 1 次 |

### 可重试错误

- 网络错误；
- HTTP 429；
- HTTP 502、503、504；
- 上游连接中断。

### 不可重试错误

- API Key 错误；
- 参数或图片格式错误；
- 内容安全拒绝；
- 用户额度不足；
- 权限校验失败。

### 降级行为

- RAG 失败：降级为无知识库回答，并记录降级状态；
- 意图模型失败：使用规则路由；
- SQL 查询失败：明确说明暂时无法读取价格，禁止自行估价；
- 图像生成失败：保留用户输入和已有图片，允许原请求重试；
- 视觉分析失败：不得切换到文本模型假装已经分析图片。

### 验收标准

- 每个主要失败场景都有确定行为；
- 不出现无限重试；
- 重试不会重复扣除用户额度；
- 重试不会产生重复业务记录；
- 降级行为能够在观测记录中识别。

## 6.8 任务八：核心流程验收与试用准备

**优先级：** P0  
**预计时间：** 0.5 天  
**依赖：** 任务一至任务七

### 十条核心验收案例

1. 无空间图，按风格生成；
2. 有空间图，无石材图；
3. 有空间图和一种石材；
4. 多种石材及不同用途；
5. 修改上一张效果图；
6. 分析上一张效果图；
7. 查询已存在材料价格；
8. 查询不存在的材料价格；
9. 图像模型超时后重试；
10. 用户连续点击生成。

每条记录：

```text
输入
预期结果
实际结果
总耗时
生成次数
估算成本
是否成功
失败原因
request_id
```

### 首批试用准备

- 准备 3 个测试账号；
- 准备 5～10 组真实庭院和石材图片；
- 清理演示材料中的错误价格；
- 确认日志无敏感信息；
- 确认用户不能访问他人图片和会话；
- 准备结构化反馈表；
- 录制 2～3 分钟操作演示。

### 验收标准

- 10 条核心案例至少 9 条成功；
- 失败案例能够通过 `request_id` 找到明确原因；
- 系统达到邀请首批用户试用的条件。
